# 增量名单、裁定与双报告

v0.9 默认把用户选定的现有飞书多维表格视为名单事实源和唯一审核工作台。系统不得要求用户维护
第二份技术表，也不得因为一次同步而重建、清空或全量重抓所有人员主页。

## 名单同步

1. 读取 Base 时保留飞书 `record_id`，并对规范化后的业务字段计算
   `record_version_hash`。行号、排序位置和显示名都不能作为唯一身份。
2. 每个来源保存最近一次**完整分页**快照。只有读取了全部页且 bridge 覆盖校验通过，才可把
   上次存在、本次缺失的记录标记为 `removed`；分页中断或字段读取失败时禁止推断删除。
3. 同步结果分为 `added`、`updated`、`unchanged`、`restored`、`removed`。只把新增、相关字段
   更新和恢复记录加入后续工作集；普通定时同步不得使用 `--force-all`。
4. 用户删除行时只做 tombstone 和暂停该名单关系。人物、来源、baseline、observation、报告和
   审核历史全部保留。若同一人物仍由另一名单引用，不暂停其有效跟踪来源。
5. 用户恢复同一 `record_id` 时取消 tombstone。只在 URL、身份锚点或跟踪状态发生变化时安排
   对应来源扫描；姓名排版、备注等变化不会导致所有主页重新抓取。

## 同一张表中的字段边界

运行时先读取完整 field-list，并把配置字段名和内置中英文别名映射到现有列，不能从非空单元格
反推 schema。缺少机器列时只做可重入的 **additive field-create**；永不重命名或删除列。缺少
人工资料列时保留原表并写开发者报告，不擅自创建第二套列。推荐列为：

- `人员编号`：稳定人物键；
- `记录类型`：区分普通`人员`与机器生成的`审核项`，审核项不得再次导入成新人物；
- `同步状态`、`跟踪状态`：机器维护的生命周期状态；
- `审核状态`、`待确认信息`：待选内容及原因；
- `审核决定`：用户维护，机器不覆盖；`暂不跟踪` 是受控关闭值；
- `管理方式`：说明字段归属。

姓名、别名、学校、研究方向、阶段、主页 URL 和 `审核决定` 都是人工字段。权威 Base 的这些
字段是 SQLite 的上游真值；其他来源与非空人工值冲突时只更新待确认信息，绝不覆盖人工值。
机器同步只对实际变化的行 upsert，且不得把失效、退役或匿名访问受限的来源重新放回主页主字段。
机器生成的审核内容直接标注原始 Base 行并复用其 `record_id`，不会复制一行，也不会产生
“审核项的审核项”。

待补主页时，用户应把 URL 填进 `个人主页`、`Google Scholar`、`GitHub` 或 `LinkedIn` 对应列；
下一次增量对账会复用原行、关闭审核并开始扫描。不要把 URL 粘进 `审核决定`。若确实不需要跟踪，
在 `审核决定` 填写 `暂不跟踪`；该决定会幂等关闭审核，系统保留行和审计但不创建人物。

## 执行 Agent 裁定

OpenClaw 无人值守由隔离宿主 Agent 回合执行：确定性层只做抽取和硬安全门，不调用 DeepSeek 或任何另行配置的模型 API。所有拟公开变化
写入 mode-0600 的 `people-tracking-agent-review-v1` 请求文件，由正在执行本 Skill 的 Agent
使用自身上下文和 token 裁定。Agent 返回内容必须完整覆盖并绑定 `review_snapshot_id`、
`request_id` 和 `evidence_hash`；过期、
缺项、重复或未知请求整批拒绝，任意一项失败时整批零写入。
单个持久快照受 `agent_review.batch_size` 限制；大积压会按顺序拆成多个精确快照，避免超出
宿主 Agent 上下文。`defer` 只终止当前不可证实的证据快照并记入开发者审计；新证据仍会重新
触发审核。

确定性规则会把新增论文、论文接收、职位或单位变化、重要奖项标为“建议发布”，但仍必须经宿主
Agent 最终批准才能进入用户报告。纯 UI 词、同文案换链接、不可解释的年份、乱码、字符级排版、
只把“博士一年级”改为“博士二年级”等硬噪声可直接抑制。无法证明是现实世界变化的内容不能
进入用户报告；选择 `defer` 时，本次事件按“不发布”终结并保留审计，而不是成为无法再次领取
的永久 pending 项。

## 双报告

- 用户报告只含已批准的重要人员变化，逐条写清“谁、什么变化、原来是什么、现在是什么、原始
  链接”。无变化时不发送空消息。
- 开发者报告使用独立游标和独立目标，包含解析异常、来源健康、429/circuit 状态、覆盖率、待
  审核项和自动修复状态。默认只生成本地私有 Markdown；如配置飞书文档，目标不得与用户报告
  相同。
- 来源错误不能阻止已确认事实进入用户报告；用户报告也不能包含错误码、解析器、覆盖率、候选
  次数或内部修复说明。

报告按时间窗口和事件账本生成，不再只引用“上一次扫描 run”。日报、周报和重试各有幂等键；
只有对应目标投递成功才推进其游标，任一报告失败不会冒充另一报告成功。

## Scholar 429

Scholar 使用持久的 host circuit 和请求预算。收到 429 或有效 `Retry-After` 后立即停止该 host
当轮余下请求，将 `blocked_until` 写入 SQLite；进程重启也不得绕过。到期后只放行小批 canary，
成功才逐步恢复。人员来源以稳定哈希分散到一周内，失败项使用有上限的指数退避；不得并发补跑
积压，也不得因名单编辑触发全量 Scholar 扫描。每轮、滚动 24 小时和滚动 7 天预算同时生效；
首次 baseline 也遵守错峰与预算，延后项由 scheduler 在一周内补齐而不是让初始化永久失败。
